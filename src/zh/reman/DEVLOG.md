# Reman（热漫）开发笔记

记录这个扩展从零到能用的过程中踩过的坑、查证过的结论、被推翻的理论。下次要修 bug 或加功能时，先看这份笔记，避免重复踩坑或重复验证已经确认过的事情。

站点：`www.yueman1.cc`（老式 qTcms 桌面模板，GB2312/GBK/GB18030 混用编码，ASP 后端），域名由 `reman.cc` 地址发布页动态发现。

## 1. WAF 滑动验证码——最大的坑，排查历时很长

### 1.1 最终确认的工作机制

请求命中 WAF 会返回 `403` + 一个引用 `/huadong_<siteId>_<key>.js` 的挑战页（HTML 里的滑块只是给人看的，脚本本身才是关键）：

1. 请求原始 URL → `403`，body 里有挑战页 HTML，引用一个 `/huadong_*.js?id=<timestamp>` 脚本。
2. 拉取这个 JS → 明文写着当前站点部署所用的 `key` 和 `value`（这组值不是每次挑战都变，是隔一段时间才整体轮换一次）。
3. 计算 `md5(stringToHex(value))`（`stringToHex` = 每个字符 ASCII 码 +1 后按十进制拼接），`type` 是站点级固定常量 `ad82060c2e67cc7e2cc47552a4fc1242`。
4. 请求验证接口 `/a20be899_96a6_40b2_88ba_32f1f75f1552_yanzheng_huadong.php?type=...&key=...&value=<md5>` → 返回 `Set-Cookie`（约 2 小时有效）。
5. 带着这个 cookie 重试原始请求 → 应该能拿到 200。

实现在 [`SlideCaptchaInterceptor.kt`](src/eu/kanade/tachiyomi/extension/zh/reman/SlideCaptchaInterceptor.kt)。

### 1.2 真正的根因（关键结论）

**JS 请求和验证请求必须带 `Referer`（指向当前页面）和真实浏览器 `User-Agent`。** 裸请求（没有这两个头）哪怕 key/value/cookie 全部正确，源站也会拒绝放行。这是排查了几十轮才定位到的真正原因——之前手写的 `GET(url)` 完全没带这些头（KeiSource 默认只给"正常"请求自动加 Referer/UA/Origin，手动构造的子请求不会自动继承）。

修法：`request.forUrl(newUrl)` 从原始请求复制完整请求头，只换 URL、把 Referer 改成当前页面地址。

### 1.3 被推翻的错误理论（教训：不要在没有对照实验的情况下下结论）

- **"Fikker 缓存代理把响应缓存住，命中缓存时连 Set-Cookie 一起丢失"**：一开始观测到验证接口返回 200 但没有 Set-Cookie，怀疑是缓存代理按 URL 字面值缓存住了旧响应。后来证实缓存确实存在（同一个 URL 短时间内重复请求会命中缓存），但**不是导致最终 403 的根本原因**——因为哪怕加了缓存穿透参数、验证接口真的返回了全新的 Set-Cookie，用这个 cookie 重试仍然 403。真正原因是 1.2 里的 Referer/UA。
- **"给内容页 URL 加缓存穿透参数（随机查询参数）"**：作为上面这个错误理论的配套措施加了这段代码，后来发现 `/manhua/{id}.html` 能容忍陌生查询参数，但 `/p/{mangaId}/{chapterId}.html` 这类章节页会因为参数把路由匹配打偏，返回 **404 而不是忽略参数**，而代码里"非 403 就当作最终结果直接返回"，于是把这个误判的 404 当成"已放行"直接返回给上层，导致看图失败。**已经整个移除**，只在验证接口（专门的 PHP 脚本，反复验证过能安全接受多余参数）上保留穿透逻辑。
- **"源站按 IP 信誉库拦截数据中心/云服务器 IP（Azure VM 等），跟滑块算法对不对无关"**：因为 Suwayomi 跑在 Azure VM 上、验证死活拿不到 session cookie，一度怀疑是这个。后来用户证实 Suwayomi 加了 Referer/UA 之后能正常工作，直接推翻了这个理论。**教训：源站愿意认真走完整套挑战流程（包括每次都给验证接口下发一个全新的真实 cookie）本身就不太像纯 IP 硬拦截的行为特征**——硬拦截通常会在更早的环节短路掉，不会陪你把整套流程走完。

### 1.4 Cookie 处理

不能指望共享 OkHttpClient 配了持久化 CookieJar——**实测 Suwayomi 这类非 Android 运行时默认没有**（OkHttp 默认 `CookieJar.NO_COOKIES`）。所以拦截器里手动把每一步下发的 `Set-Cookie` 收集起来（按 cookie 名去重合并，新的覆盖旧的），显式塞进下一步请求的 `Cookie` 头。

## 2. 本地测试 IP 被封——未来会不会解封不确定

在排查过程中，我（Claude 这边的沙盒环境）对该站点做了大量高频测试请求，测到后期这个测试 IP 被站点限流/封锁得越来越严重：从"只有搜索接口偶尔 403"逐渐恶化到"几乎所有动态路由（分类页、漫画详情页）都直接 `000`/Empty reply from server"，只有首页还能访问。**这个状态截至笔记写下时仍未恢复，不确定未来会不会自然解封（比如按时间窗口重置）。**

影响：下次如果还需要我（agent）直接对着真实站点做实验性验证，大概率还是会遇到这个问题，建议：

- 优先让用户在他们自己的网络环境（比如手机热点，用户已经证实过可用）里测试、把日志/HTML 贴回来，而不是指望我这边能直接验证。
- 如果我这边网络状态好转，验证前先用一两个轻量请求（比如首页）探一下路，不要一上来就密集测试。

## 3. Suwayomi 特有的运行时坑（跟 WAF 无关，但同样费了不少时间）

### 3.1 `kotlinx.serialization` 在 Suwayomi 下崩溃

`@Serializable` 数据类编译时会生成 `$$serializer` companion class（实现 `GeneratedSerializer` 接口，带默认方法）。Suwayomi 不跑真安卓，是把打出来的 APK 用 **dex2jar** 转换回 JVM class 文件再加载运行的，这种编译器插件生成的、带接口默认方法脱糖产物的类，在 dex→jar 反向转换时会丢失/损坏，运行时报 `NoClassDefFoundError: kotlinx/serialization/internal/GeneratedSerializer$-CC`。

这跟 [`build.gradle.kts`](build.gradle.kts) 里那条关于 R8 minify 破坏 dex2jar 转换的注释是**同一类问题的另一种表现**（不是同一个 bug，但病根类似：dex2jar 转换对某些编译产物不友好）。

修法：不用 `@Serializable`/`parseAs<T>()`，改用 `org.json.JSONObject`/`JSONArray` 手动解析——纯 Android SDK 自带类，没有编译器插件生成代码，不会有这个兼容性问题。参考 `quickSearch()` 的实现。

**以后这个扩展里如果要新增任何 JSON 解析，一律用 `org.json`，不要用 `kotlinx.serialization`。**

### 3.2 章节页编码问题

页面声明 `<meta charset=gb2312>`，但实际会发繁体字等超出 GB2312 范围的字节（比如章节名"血脈賁張"）。`keiyoushi.utils.asJsoup()` 默认信任页面声明的 charset，用 GB2312 解码这些字节会产生乱码（用户截图里的 `血�}�S��` 就是这么来的——GB2312 解码到非法字节序列时错位，把本应是多字节字符的后半字节当成了独立 ASCII 字符）。

修法：不用共享的 `asJsoup()`，自己实现 `Response.asGbkJsoup()`，强制用 **GB18030**（GBK 的超集，兼容性最好）解码，不信页面自己声明的 charset。已经用实际字节验证过：GB2312 解码这段数据会直接报错，GBK/GB18030 能正确解出"血脈賁張"。

### 3.3 章节列表顺序

站点 HTML 原始顺序是**新章节在前**。Tachiyomi/Suwayomi 默认按扩展**返回列表的原始顺序**展示（不会自动重排），如果对列表做 `.asReversed()`，会导致最旧的章节排到 UI 最顶部——这正是之前的实现方式，是个真 bug。

修法：不反转列表本身，保持站点原始顺序（新在前）；`chapter_number` 用"总数 - 位置下标"计算（最旧=1，最新=总数），这样排序和编号可以同时满足，互不影响。

### 3.4 卷/话混排——已知但不打算解决

个别漫画的章节列表里，"第X话"（单话）和"第X卷"（合订本）混在同一个列表里，顺序也不完全规整（比如早期内容只有卷，后期改成逐话更新，中间偶尔还会插一本合订卷）。这是**站点自己的数据组织问题**，不是我们解析错了。

已经确认：
- Tachiyomi/Suwayomi 的 `SChapter` 模型没有单独的"卷"字段，APP 本身没有卷/话分离功能。
- 尝试用标题关键字（"第X卷" vs "第X话"）区分风险较高（不同漫画标题格式可能不一致，没法逐本验证），投入产出比不高。

**结论：暂不处理，排序 bug（3.3）修好之后，这个问题从"排在最顶部很怪异"降级为"列表中间偶尔有一本卷混进去"，观感可以接受。** 如果以后要做，需要用户提供更多不同漫画的章节列表样本，先验证"卷"标题的格式是否统一，再决定要不要加区分逻辑（大概率需要一个 source 设置项，而不是自动判断）。

## 4. 关键词搜索

- 站点自带的 `search.asp` 表单搜索接口**本身是坏的**——不管验证码是否通过、关键词是什么（含空关键词），一律固定返回 6 字节的 `soyyr!`，不是正常结果页。已确认跟验证码/编码无关，就是接口本身返回异常占位内容，等站点自己修。**不要再尝试接入这个接口。**
- 改用移动版页面 (`m.yueman1.cc`) 背后同款的 JSON 快速搜索接口：`GET $baseUrl/template/skin4_20110501/images/m/html/?a=3&key=<GBK 编码的关键词>`。这个接口实际挂在 **PC 域名** `www.yueman1.cc` 下（跟移动版页面本身是两个不同的主机），同样受滑动验证码保护，走同一套 `SlideCaptchaInterceptor`。
- 关键词必须按 **GBK**（不是 UTF-8）编码后手动做百分号编码提交，参考页面表单本身的 `charset=gb2312` 声明（实际是 GBK）。
- 响应格式是 `var success_data=<json>` 这样一整段 JS 变量赋值语句，不是裸 JSON，需要先 `removePrefix`。

## 5. 错误诊断——已加的机制

之前调试过程中最痛的一点：`getPageList()` 等函数遇到页面结构不符合预期时会**静默返回空列表**，完全看不出是验证码没过、页面改版了、还是别的问题，只能靠临时加 debug log、重装重测才能定位。

已加 `parseError(what, url, content)` 统一辅助函数（[Reman.kt](src/eu/kanade/tachiyomi/extension/zh/reman/Reman.kt)）：任何"页面结构假设不成立"的地方（选择器找不到容器、响应格式不对、`getPageList` 解码出来的 URL 格式非法等）都改成抛出这个异常，异常信息里带上 URL 和实际收到的内容片段（截断到 800 字符），配合 Kotlin 异常自带的 stack trace，用户可以直接复制异常详情反馈排查，不用再开 debug log 重跑。

**以后新增解析逻辑，凡是"选择器/正则/格式假设不成立"的分支，默认用 `parseError` 而不是静默返回空值/空列表。**

区分"我们抓错了"还是"链接真的失效了"的方法（针对 `getPageList` 的图片 URL 尤其有用）：
- 抓出来的 URL **格式本身非法** → 我们的 bug → 现在会在生成页面列表这一步直接抛 `parseError`。
- URL 格式合法，但**运行时请求失败**（DNS 解析不到、连接超时等，异常来自 `HttpSource.getImage`，不是我们扩展自己的代码）→ 内容本身在源站已经失效（老旧图床域名过期之类），不是我们的问题，无法修，属于"认了"的范畴。

## 6. Suwayomi 调试日志留存

`SlideCaptchaInterceptor` 里的 `Log.d(TAG, ...)` 全部保留，不要删。这套日志是排查这一路问题的主要信息来源，下次再遇到验证码相关的问题，第一步先让用户把这些日志贴过来，能省掉大量来回试探。

日志覆盖的关键节点：挑战页命中、JS 拉取结果、key/value/md5 计算结果、验证接口的完整响应（含 Set-Cookie）、最终重试结果，每一步都带 `Set-Cookie`/`Cache-Control`/`Date`/`X-Via`/`Content-Length` 这几个关键响应头。

## 7. 目前的已知限制 / 可能的后续方向

- 关键词搜索走 JSON 快速搜索接口（见第 4 节）；只有"不选分类、关键词留空"这一种情况（默认浏览态）才会退回到"最新更新"+"完结漫画"列表的客户端过滤。
- 卷/话混排问题未处理（见 3.4），如果用户反馈体验不好，可以考虑加 source 设置项。
- 老旧图片链接失效的情况没有主动预检/过滤（见第 5 节末尾），目前认为不值得为此增加请求开销。
- 如果站点将来更换了滑块验证的具体实现（`key`/`value`/`type` 的位置、验证接口路径等），`SlideCaptchaInterceptor.kt` 里的正则和路径常量需要跟着更新——第 6 节提到的调试日志是届时排查的第一手资料。
